## 一句话总结

Composer 2 是 Cursor 团队基于 Kimi K2.5 基座模型，通过两阶段专业化训练（持续预训练 + 大规模强化学习）打造的软件工程智能体模型，在 CursorBench 上较上一代提升 37%，以更低推理成本达到前沿水平。

---

## 背景与问题

### 研究背景

随着大语言模型在代码生成领域取得突破性进展，将通用基座模型适配为真实工程场景下的智能体（Agent）成为核心挑战。Cursor 作为 AI 编程工具的代表，其核心模型 Composer 需要处理：

- **大规模代码变更**：真实工程 session 中代码改动中位数达 181 行，而公开基准（如 SWE-bench）仅 7-10 行
- **简短、模糊的指令**：真实用户提示中位数仅 390 字符，远少于学术基准的 1185-3055 字符
- **多维度质量要求**：不仅需要功能正确性，还需兼顾代码质量、意图理解、指令遵从、打断处理等

### 公开基准的四大局限

| 局限性 | 说明 |
|--------|------|
| 域不匹配（Domain mismatch） | 公开基准不能反映 Cursor 真实用户的使用模式 |
| 提示过度规范（Prompt over-specification） | 学术提示比真实提示详细 3-8 倍，遮蔽了真实难度 |
| 数据污染（Data contamination） | 训练数据可能已包含测试集内容 |
| 评估范围狭窄（Narrow evaluation scope） | 仅测试功能正确性，忽略其他工程质量维度 |

## 核心方法

### 1. 基座模型选择

团队系统评估了三款候选基座模型：GLM-5、Kimi K2.5、DeepSeek V3.2，最终选择 **Kimi K2.5**（1.04T 参数，32B 激活参数，混合专家架构 MoE）。

评估维度：
- **FreshBench**（代码知识新鲜度）：Kimi K2.5 得分 83.2%，表现最优
- **状态追踪**（LoCoDiff 风格）：字符编辑距离 86，最优
- **代码库困惑度**：在 Cursor 私有单仓库上测量

---

### 2. 两阶段训练流程

#### 第一阶段：持续预训练（Continued Pretraining）

分为三个子阶段：

```
子阶段 1：32k token 序列长度的大规模预训练
子阶段 2：长上下文扩展至 256k token
子阶段 3：针对编码任务的短序列 SFT（监督微调）
```

**关键技术细节：**
- 使用 MXFP8 混合精度训练，硬件为 NVIDIA B300
- 优化器：AdamW
- 损失函数：交叉熵损失呈对数线性下降，且被发现是下游 RL 性能的有效预测指标
- **多 Token 预测（MTP）**：通过自蒸馏训练额外的 MTP 层，用于生产环境中的投机解码（Speculative Decoding），提升推理速度

---

#### 第二阶段：强化学习（Reinforcement Learning）

采用策略梯度方法，核心设计如下：

**算法选择与改进（相对于标准 GRPO）：**

| 改进点 | 具体做法 | 原因 |
|--------|----------|------|
| 去除长度标准化 | 参考 Dr. GRPO，移除组内长度归一化 | 避免对不同长度响应产生偏差 |
| 不对组优势做标准差归一化 | 保留原始优势值尺度 | 保持训练信号的真实幅度 |
| 不屏蔽超长 rollout | 允许所有长度的序列参与训练 | 避免截断有价值的长推理链 |
| KL 估计器 | 使用 k₁ = −log r 替代 k₃ | 避免大 KL 值时的方差爆炸问题 |
| MoE 路由重放 | 对齐推理和训练时的专家路由 | 消除训练-推理分布偏差 |

**自摘要机制（Self-Summarization）：**

将多轮生成串联，并在每轮之间插入摘要；最终奖励应用于所有 token。

- 相比基于提示的上下文压缩，减少了误差累积
- 使用更少的 token 维持长上下文任务的连贯性

**长度惩罚（Length Penalty）：**

采用非线性凹函数惩罚：

$$C_{length}^{k,q}(x) = \frac{(1+kx)^{1-q} - 1}{k(1-q)}$$

该函数的设计特点：
- 对简单任务：施加较强惩罚，鼓励简洁回答
- 对困难任务：允许更长推理，支持深度思考
- 整体激励效率，避免无意义的 token 堆砌

---

### 3. CursorBench：专属评测基准

CursorBench 从真实 Cursor 工程 session 中构建，全面评估以下维度：

| 评测维度 | 说明 |
|----------|------|
| 功能正确性 | 代码能否正确运行 |
| 意图理解（Intent） | 是否理解用户真实意图 |
| 指令遵从（Instruction-following） | 是否遵守明确指令 |
| 主动编辑（Eager editing） | 是否适度主动提出改进 |
| 代码质量（Code quality） | 生成代码的工程质量 |
| 打断处理（Interruption handling） | 被中断后的恢复和处理能力 |

---

### 4. 训练基础设施

#### 训练侧
- **并行策略**：上下文并行（CP）为长上下文主要轴；专家并行（EP）与张量并行（TP）解耦
  - 预训练：EP=8, CP=2
  - RL：EP=8, CP=8
- **自定义内核**：CUDA/PTX/ThunderKittens 内核；针对 MoE 前向传播的新型 NVFP4（带 per-token FP8 scale）；MXFP8 用于反向传播
- **全局序列打包**：每次 RL 训练步骤前进行，实现数据并行负载均衡

## 实验结果

### 主要性能对比（Table 1）

| 模型 | CursorBench | SWE-bench Multilingual | Terminal-Bench |
|------|:-----------:|:---------------------:|:--------------:|
| **Composer 2** | **61.3** | **73.7** | **61.7** |
| Composer 1.5 | 44.2 | 65.9 | 47.9 |
| Composer 1 | 38.0 | 56.9 | 40.0 |
| Kimi K2.5（基座） | 36.0 | 65.1 | 47.3 |
| GPT-5.4 | 63.9 | 76.8 | 66.5† |
| Opus 4.6 High | 58.2 | 75.8 | 58.0 |

### 关键发现

1. **代际提升显著**：Composer 2 相比 Composer 1.5 在 CursorBench 上实现 **37% 相对提升**（44.2 → 61.3）

2. **专业化训练的价值**：基座 Kimi K2.5 在 CursorBench 上仅得 36.0 分，经过两阶段专业化训练后提升至 61.3，**提升幅度达 70%**，证明领域专业化训练的巨大价值

3. **接近最强前沿模型**：与 GPT-5.4（63.9）和 Opus 4.6 High（58.2）相比，Composer 2 以更低推理成本实现了竞争性性能

4. **多语言能力突出**：SWE-bench Multilingual 得分 73.7，超越 Opus 4.6 High（75.8）和 Kimi K2.5 基座（65.1）

5. **交叉熵损失的预测性**：预训练阶段的交叉熵损失被发现是下游 RL 性能的有效预测指标，为训练早停和超参选择提供了实用信号

## 总结

### 技术贡献

Composer 2 的核心贡献在于系统性地展示了如何将通用强基座模型通过领域专业化训练转化为顶级软件工程智能体：

- **基座选择方法论**：通过领域相关指标（FreshBench、状态追踪、代码库困惑度）系统选择最适合的基座
- **改进的 GRPO 算法**：多项针对长上下文代码任务的算法改进（去长度偏差、KL 估计器优化、MoE 路由对齐）
- **自摘要机制**：解决长 horizon 任务中的上下文压缩问题
- **内部评测基准**：CursorBench 提供了比公开基准更真实、更全面的工程场景评测

### 局限性与未来方向

- 当前模型在需要数小时人工时间的**超长 horizon 任务**上仍有提升空间
- 未来工作将专注于扩展 Agent 处理更复杂、更长时间跨度工程任务的能力

### 对行业的启示

1. **领域专业化 > 通用规模扩展**：针对特定场景的专业化训练可以以低于 frontier 模型的推理成本达到竞争性性能
2. **内部评测基准的重要性**：公开基准与真实产品场景存在显著差距，构建产品相关的评测体系是必要的
3. **基础设施的系统性挑战**：大规模 RL 训练需要训练、环境、推理、评估四个解耦服务的协同设计，工程复杂度不亚于算法创新
