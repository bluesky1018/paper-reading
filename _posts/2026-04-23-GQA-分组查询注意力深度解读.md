## 一句话总结

提出 **GQA (Grouped-Query Attention)** —— 在 **Multi-Head Attention (MHA, Q/K/V 每头独立)** 和 **Multi-Query Attention (MQA, K/V 全部头共享一份)** 之间做**可调的中间态**:Q 头分成 $G$ 组,每组共享一份 K/V。再加上 **uptraining**(从已有 MHA checkpoint 微调成 GQA) 技巧,实现 "**推理速度接近 MQA、质量接近 MHA**"。从此 GQA 成为所有现代大模型的**事实标准**。

## 背景:Decode 端的瓶颈不是算力,是显存带宽

### Multi-Head Attention 的 KV cache

自回归生成(decode 阶段)里,每生成一个新 token 要把之前所有 token 的 K、V 从 HBM 读进 SRAM 算一次 attention。KV cache 大小:

$$
\text{KV cache size} = 2 \times B \times N \times H \times d_h \times \text{bytes}
$$

其中 $B$ = batch,$N$ = 序列长度,$H$ = 头数,$d_h$ = head dim。以 LLaMA-65B 为例($H=64, d_h=128$,bf16),context=8K、batch=64 时 KV cache 占 **~128 GB**,远超 A100 单卡 80GB。

**decode 阶段每生成一个 token 都要把整个 KV cache 读一遍**——典型 memory-bound,这是制约 tokens/s 的瓶颈。

### 前人:MQA(Shazeer 2019)

Shazeer 提出把 **所有 Q 头共享一份 K/V**:

$$
H_{kv} = 1
$$

直接把 KV cache 压 $H$ 倍(64 头 → 2 GB)。代价是质量下降——共享太狠,模型表达力受损。

### 本文要解决的问题

1. **MQA 质量下降多少?能不能不从头训?** —— 之前都需要 from scratch,训练成本高
2. **MHA 和 MQA 中间有没有更好的 trade-off?**

GQA 同时回答了这两个问题。

## 核心机制

### GQA 架构

![三种注意力对比:MHA(H 个独立 Q/K/V 头)、GQA(H 个 Q 头分 G 组,每组共享 1 份 K/V)、MQA(H 个 Q 头全部共享 1 份 K/V)。GQA 是 MHA 与 MQA 的 interpolation。](/assets/img/gqa/x2.png)
_Figure 2:MHA / GQA / MQA 架构对比——GQA = 在两者之间的可调中间态_

给定查询头数 $H$ 和 GQA 组数 $G$:

- **MHA**:$H_{kv} = H$(每头独立)—— 旧架构
- **GQA-G**:$H_{kv} = G$(每 $H/G$ 个 Q 头共享一份 K/V)—— 本文方案
- **MQA**:$H_{kv} = 1$(全部共享)—— 前人方案

显然 GQA 是前两者的泛化:$G = H$ 退化为 MHA,$G = 1$ 退化为 MQA。

### Uptraining:从 MHA 无痛迁移

**关键问题**:已有的 MHA checkpoint(几百 B 参数、训练成本上千万美元)能不能直接改成 GQA,不用从头训?

作者的方案:

1. **K/V 头聚合**:把每组 $H/G$ 个头的 K/V 投影矩阵**做均值池化**(mean pool),得到一份共享的 K/V 投影(recycling,见 Figure 1)
2. **Uptrain**:用小比例(通常 $\alpha = 5\%$ 的原始预训练步数)继续训练,让模型适应新结构

这样**总训练成本 ≈ 原 MHA 训练的 5%**,却能拿到几乎等同 MHA 的质量 + 几乎等同 MQA 的速度。

## 实验:质量 × 速度 × Uptraining 比例

作者用 T5-XXL 11B 做所有实验,在多个 NLG 任务(CNN/DailyMail、arXiv、PubMed、MediaSum、MultiNews、WMT、TriviaQA)上评估。

### 主结果表

| 模型 | 推理时间 (s) | Avg R1 | WMT BLEU | TriviaQA F1 |
|------|-------------|--------|----------|-------------|
| MHA-Large | 0.37 | 43.4 | 27.7 | 78.2 |
| MHA-XXL | 1.51 | 43.6 | 28.4 | 81.9 |
| MQA-XXL | **0.24** | 43.4 | 28.5 | 81.3 |
| **GQA-8-XXL** | **0.28** | **43.7** | **28.5** | **81.7** |

**GQA-8 几乎与 MHA 持平**(甚至略好),而**推理速度比 MHA-XXL 快 5.4×**。

### 关键发现

- **越大的模型越从 GQA/MQA 受益**:MQA/GQA 的相对速度增益随模型变大而放大,因为 KV cache 的绝对读取量随 $H, d_h$ 线性增长
- **Uptraining $\alpha = 5\%$ 足够**:再多提升有限。说明 GQA 与 MHA 结构兼容度很高,5% 的 re-adaptation 就能稳定收敛
- **组数 $G = 8$ 是甜点**:从 $G = 1$(MQA)增到 $G = 8$ 质量明显提升,再到 $G = 64$(近 MHA)收益递减,但推理开销接近 MHA

### Uptraining 激活方式消融

文章对比 3 种 K/V 投影初始化方式:

| 方法 | 说明 | 相对表现 |
|------|------|---------|
| **Mean** (本文) | 所有头参数均值 | ✅ 最优 |
| First | 只用第一个头 | 中等 |
| Random | 随机初始化 | ❌ 最差 |

**Mean 赢**——它保留了所有原头的信息,而不是丢弃或从头训。

## 为什么 GQA 成为事实标准

### 1. 推理经济学的胜利

在部署场景里,KV cache 大小直接决定三件事:

- **单卡能装多少用户**(高 batch = 高吞吐)
- **上下文能开多长**(长 context 应用)
- **tokens/s**(用户体验)

GQA 一次性同时改善三项。LLaMA-2 70B 从 MHA 切换到 GQA (G=8) 后:

- KV cache 从 80 GB → 10 GB
- 吞吐提升 ~4×
- 质量损失几乎不可测

**这就是为什么 LLaMA-2 70B、LLaMA-3、Mistral、Qwen2/3、Gemini、Claude 等几乎所有新一代大模型都使用 GQA**。

### 2. Uptraining 让迁移零成本

已经训好的 MHA 模型不用扔。5% 预算就能改造成 GQA——这对工业界迁移巨大友好。这个"从已有 checkpoint 做架构手术"的范式后来启发了 MoE upcycling、量化感知 fine-tuning 等一众工作。

### 3. 给 Flash/Paged Attention 留足空间

GQA 只改了 K/V 头数,对 FlashAttention 的 tiling 完全透明——K/V 在每组内广播到对应 Q 头即可,CUDA 实现几乎无成本。PagedAttention 里 KV cache 小了 $H/G$ 倍,直接享受相应的显存/吞吐提升。

### 4. 后继者仍然基于它

| 后续工作 | 相对 GQA 的定位 |
|---------|----------------|
| **MLA** (DeepSeek-V2/V3) | K/V 先压到 latent 再升回,KV cache 比 GQA 再小一个数量级 |
| **Linear Attention** (Mamba、Gated DeltaNet) | 完全绕过 KV cache,但 full attention 层仍用 GQA |
| **Hybrid** (Jamba、Qwen3.5) | full attention 层基本都是 GQA |

所以即使未来 attention 范式在变,GQA 作为"full attention 里做 KV 节省"的标准方案几乎不会被替代。

## 读完这篇你真正该带走的 4 件事

<callout emoji="white_check_mark" background-color="light-green" border-color="green">
1. **Decode 阶段的瓶颈是 KV cache 带宽,不是算力**:理解了这条才能理解 MQA/GQA/MLA 为什么一直在往"压 K/V"方向走
2. **GQA = MHA 与 MQA 之间的可调插值**:$G$ 是旋钮,根据质量要求和推理成本权衡
3. **5% uptraining 就够**:结构微调 + 小规模重训,是把已有大模型"现代化"的高性价比方式
4. **mean pooling 是 "recycling" 的最佳选择**:保留信息量的量化实验支持,比随机初始化或丢头都好
</callout>
