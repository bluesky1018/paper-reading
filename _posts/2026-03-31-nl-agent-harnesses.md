## 一句话总结

本文提出将 Agent 执行框架（Harness）中散落在控制代码、工具适配器和运行时约定中的设计模式层，显式化为可编辑、可迁移、可消融的自然语言制品（NLAH），并通过智能执行运行时（IHR）将其落地，在 SWE-bench Verified（80.0%）和 OSWorld（47.2%）上取得了有竞争力的结果。

---

## 背景与问题

### Agent 的成败取决于 Harness

现代 LLM Agent 的性能不仅取决于模型本身，更取决于围绕模型构建的**执行框架（Harness）**——管理多步推理、工具调用、记忆、任务委派和终止条件的控制栈。

经典的 Harness 模式包括：
- **ReAct**（Yao et al., 2023）：推理-行动循环
- **RAG**（Lewis et al., 2021）：检索增强生成
- **Reflexion**（Shinn et al., 2023）：通过自我反馈进行语言强化学习

随着 Agent 能力的进化，领域已演进至显式记忆与自我进化、工作流生成、多智能体编排和长上下文状态管理。这将"提示工程"置于更宽泛的**上下文工程**框架下：决定在每个步骤中哪些指令、制品和状态是可用的。

### 核心问题

**Harness 逻辑碎片化**：现有 Harness 的设计模式层散落在控制器代码、框架默认值、工具适配器、验证脚本和运行时假设中，导致：
- 难以跨框架迁移
- 难以进行科学对比
- 难以精确消融实验

### 研究动机

AGENTS.md 和技能包等自然语言制品已证明，可移植文本能打包可重用的过程知识。但这些仅建立了**可重用控制知识**的可行性，而非具备联合执行合约、角色和运行时适配器的**显式可执行 Harness 表示**。

### 核心问题

> Harness 中的设计模式层能否被显式化为一个**可执行的自然语言对象**？

## 核心方法

### 整体架构

![论文架构图](https://arxiv.org/html/2603.25723/x1.png)

本文提出了两个核心组件：
1. **NLAH（Natural-Language Agent Harnesses）**：以可编辑自然语言表达 Harness 行为的制品
2. **IHR（Intelligent Harness Runtime）**：通过显式合约、持久制品和轻量级适配器执行 NLAH 的共享运行时

### 2.1 Harness 与模式层

Harness 管控多个模型/Agent 调用，规定：
- **控制**：工作如何分解和调度
- **合约**：所需制品、关卡、终止规则
- **状态**：跨步骤、分支和委派工作者持久化的内容

### 2.2 智能 Harness 运行时（IHR）

由于 NLAH 以自然语言写成，IHR 将一个 LLM **内置到运行时循环中**。每一步，该 LLM 读取：
1. Harness 文本
2. 当前状态/环境
3. 运行时宪章（Runtime Charter）

然后选择下一个动作。

IHR 的三个核心组件：
| 组件 | 功能 |
|------|------|
| **内循环 LLM** | 解释 Harness 逻辑 |
| **后端** | 提供终端工具和多 Agent 接口（派生/监督子 Agent）|
| **运行时宪章** | 定义合约、状态、编排和子 Agent 生命周期的语义 |

**从模型调用到 Agent 调用的提升：**

单次补全被提升为一次 Agent 调用，受执行合约约束，涵盖：
- 所需输出
- 预算限制
- 权限范围
- 完成条件
- 输出路径

### 2.3 自然语言 Agent Harness（NLAH）组件

![NLAH组件图](https://arxiv.org/html/2603.25723/x2.png)

NLAH 承载**可编辑、可检视的编排逻辑**，同时适配器和脚本提供确定性钩子：

| 组件 | 描述 |
|------|------|
| **合约（Contracts）** | 所需 I/O、格式约束、验证关卡、重试/终止规则 |
| **角色（Roles）** | 求解者、验证者、研究者、编排者——不重叠 |
| **阶段结构（Stage Structure）** | 显式拓扑（如：规划→执行→验证→修复）|
| **适配器与脚本（Adapters & Scripts）** | 确定性动作的命名钩子（测试、验证器、检索）|
| **状态语义（State Semantics）** | 跨步骤持久化内容及其重新打开方式 |
| **失败分类（Failure Taxonomy）** | 驱动恢复的命名失败模式 |

### 2.4 文件支持状态模块

长时间自主运行在状态隐式或短暂时会失败。可选的文件支持状态模块将持久状态外化到路径可寻址制品中，强制执行三个属性：
- **外化（Externalized）**：状态写入制品，而非临时上下文
- **路径可寻址（Path-addressable）**：后续阶段通过路径重新打开精确对象
- **压缩稳定（Compaction-stable）**：状态在截断、重启和委派中幸存

## 实验结果

### 研究问题

- **RQ1（行为效果）**：共享运行时宪章和 Harness 逻辑在固定预算下是否改变 Agent 行为？
- **RQ2（可组合性）**：模块能否在模式层进行组合和消融？
- **RQ3（迁移）**：原生代码 Harness 与重建的 NLAH 之间存在哪些差异？

### 实验配置

- **模型**：GPT-5.4（Codex CLI v0.114.0），推理努力 = xhigh
- **硬件**：Ubuntu 24.04，64 CPU 核心，251 GiB RAM，Docker 容器
- **基准测试**：SWE-bench Verified（125 样本）、OSWorld（36 样本）

### RQ1：行为效果（表1）

| 基准测试 | Harness | 设置 | 性能 | 提示词 Token | 工具调用 | LLM 调用 | 运行时间（分钟）|
|---------|---------|------|------|------------|---------|---------|--------------|
| SWE Verified | TRAE | Full IHR | 74.4% | 16.3M | 642.6 | 414.3 | 32.5 |
| SWE Verified | TRAE | w/o RTS | 76.0% | 11.1M | 451.9 | 260.5 | 16.6 |
| SWE Verified | TRAE | w/o HS | 75.2% | 1.2M | 51.1 | 34.0 | 6.7 |
| SWE Verified | Live-SWE | Full IHR | 72.8% | 1.4M | 58.4 | 41.4 | 7.6 |

**关键发现：**
- **过程指标**（Token、调用次数、运行时间）的变化远大于解决率的变化
- TRAE Full IHR 约 90% 的使用量发生在**委派的子 Agent 中**
- Full IHR 充当**已解决集合替换器**，而非均匀前沿扩展器
- 最具信息量的失败是**对齐失败**：Harness 以不总是符合基准接受标准的方式重塑局部成功信号

### RQ2：Harness 模式消融（表3）

| 基准测试 | 基础 | 文件状态 | 证据支持 | 验证器 | 自我进化 | 多候选 | 动态编排 |
|---------|------|---------|---------|------|---------|------|---------|
| SWE Verified | 75.2% | +1.6 (76.8%) | +1.6 (76.8%) | -0.8 (74.4%) | **+4.8 (80.0%)** | -2.4 (72.8%) | 0.0 (75.2%) |
| OSWorld | 41.7% | **+5.5 (47.2%)** | 0.0 (41.7%) | -8.4 (33.3%) | +2.7 (44.4%) | -5.6 (36.1%) | +2.7 (44.4%) |

**三个关键模式：**
1. 模块效果集中在**小型已解决前沿**，而非均匀偏移
2. 模块分为两类：
   - **改善解决循环**：自我进化（收紧接受门控的尝试循环）
   - **改善过程结构**：文件支持状态、证据支持回答（提高可审计性/交接）
3. 更明确的结构 ≠ 更好的性能：验证器和多候选搜索可能增加开销而不改善结果

**关键洞察——自我进化的真正价值：** 其收益在于"一个更有纪律的接受门控尝试循环，保持搜索狭窄直到失败信号证明另一次尝试是合理的"——而非开放式反思。

**反例（sympy-23950）：** 验证器报告本地"已解决"，而官方评估器仍然失败——展示了局部接受与基准接受之间的分歧。

### RQ3：代码到文本的 Harness 迁移（表5）

| 基准测试 | Harness | 实现方式 | 性能 | 提示词 Token | Agent 调用 | LLM 调用 | 运行时间（分钟）|
|---------|---------|---------|------|------------|-----------|---------|--------------|
| OSWorld | OS-Symphony | 代码 | 30.4% | 11.4M | 99 | 1.2k | 361.5 |
| OSWorld | OS-Symphony | **NLAH** | **47.2%** | 15.7M | 72 | 34 | **140.8** |

**关键行为差异：**
- **原生 OS-Symphony**：基于截图的修复循环（验证→检查→选择 GUI 操作→重试）
- **NLAH 实现**：以文件支持状态和制品支持验证为中心；在文件/Shell/包操作能提供更强完成证书时，从脆弱的 GUI 修复切换过来

**拓扑转变：**
- 原生：36 个主轨迹 + 7 个短嵌套搜索轨迹（桌面控制循环）
- 迁移后：34 个保留的内部事件流（合约优先的运行时流，状态在任务文件/账本中）

**验证转变：** 原生轨迹通常基于**屏幕合理性**停止；迁移运行在路径可寻址证据（写入的文件、重新打开的文档、包对象、系统查询）上关闭。

**轨迹密度：** 原生平均 18.1 步；迁移后平均 18.2 个唯一命令启动，但 58.5 个总记录事件——额外密度反映可观测性和恢复脚手架，而非更多任务操作。

## 讨论

### 代码 vs. 自然语言

作者**不主张**自然语言应该替代代码：
- **自然语言**承载可编辑的高级 Harness 逻辑
- **代码**负责确定性操作、工具接口和沙箱执行

争论点在于**比较单元**。

### 为什么自然语言仍然重要

与其说自然语言对单次提示措辞很重要（随着模型变强，收益可能递减），不如说它对指定**Harness 级控制**很重要：
- 角色
- 合约
- 验证关卡
- 持久状态语义
- 委派边界

### 搜索 Harness 表示

一旦 Harness 成为显式对象，它们就成为一个**搜索空间**——支持检索、迁移、重组和系统消融。这指向"对 Harness 表示进行自动搜索和优化，而非不透明的包工程"。

---

## 总结

本文的核心贡献在于将长期以来隐藏在代码中的 Agent 执行框架设计模式层**显式化、可编辑化、可执行化**。

**主要贡献：**
1. 将 Harness 设计模式层形式化为独立的表示对象
2. 定义 NLAH 的表示成分：合约、角色、阶段结构、适配器、脚本、状态语义、失败分类
3. 构建共享智能运行时 IHR，将宪章与 Harness 逻辑分离
4. 在 SWE-bench Verified 和 OSWorld 上通过受控实验验证

**核心洞察：**
- Harness 是 Agent 性能的重要决定因素，但此前缺乏科学研究工具
- NLAH+IHR 使 Harness 成为**一等研究制品**：可比较、可消融、可迁移
- 这为"Harness 表示科学"开辟了道路——Harness 模块成为可搜索、可优化的研究对象

**局限性：**
- 自然语言精度不如代码；某些机制无法从文本中忠实恢复
- 强共享宪章可能吸收本应归因于 Harness 文本的行为（运行时污染风险）
- 模块级消融不是严格的因果识别；文本表示可能引入显著性/长度混淆变量

**更广泛影响：**
可移植的 Harness 逻辑可以降低开发成本并提高可比性，但也降低了传播危险工作流的门槛。建议保障措施：来源追踪、审查、权限控制和沙箱隔离。
