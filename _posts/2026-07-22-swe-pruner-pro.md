> 🏢 **机构**：字节跳动（ByteDance）/ 上海交通大学

## 一句话总结

SWE-Pruner Pro 发现编程智能体在读取工具输出时其骨干模型的内部表示已经编码了逐行的相关性信号，因此无需额外评分模型，只需附加一个轻量"剪枝头"直接从骨干的隐藏状态中做逐行保留/剪枝决策，即可在两种主流骨干和四个多轮基准上节省高达39%的 token，同时在 SWE-Bench Verified 上为 MiMo-V2-Flash 提升 +3.8% 的解决率。

## 背景与问题

### 编程智能体的上下文膨胀问题

当前基于 LLM 的编程智能体通过与代码仓库环境交互来完成软件工程任务：它们反复调用 `cat`、`grep`、`ls`、`python` 等工具，观察原始文本输出，再继续推理。在实际任务中，**单次轨迹的 token 预算大部分被工具输出占据**——在 SWE-Bench Verified 上，文件读取命令占 Mini-SWE-Agent（使用 Claude Sonnet 4.5 作为骨干）消耗 token 总量的超过 70%，且这些输出随着轨迹推进会持续积累在上下文窗口中。

大量冗余的工具输出内容导致两个关键问题：
1. **成本膨胀**：无效内容占据大量上下文 token，直接增加推理成本
2. **长上下文性能退化**：已有研究表明 LLM 在超长上下文下存在"迷失在中间"问题，影响任务完成质量

### 现有方法的局限

现有的两类解决思路各有明显不足：

**通用提示/代码压缩方法**（如 LLMLingua、LongCodeZip）使用困惑度或语法结构等固定指标对 token 评分，无法适应智能体在任务执行中不断变化的关注焦点。

**任务特定剪枝方法**（如 SWE-Pruner）虽然能根据智能体意图做条件判断，但需要两个代价：一个独立的评分模型，以及智能体每轮必须主动生成一个"目标提示查询"（goal-hint query）以告知外部评分器当前关注的内容。

这两类方法都从智能体外部获取剪枝信号，即使骨干模型在处理工具输出时已经完成了正向传播并形成了内部表示。

### 关键洞察

本文提出了一个核心假设：**骨干模型读取工具输出时已经通过注意力加权的正向传播编码了哪些行对下一步推理重要——这个信号已经内含于最后一层隐藏状态中，不需要外部模型来重建。**

## 核心方法

### 动机验证：内部表示的线性探测

![线性探测结果](https://arxiv.org/html/2607.18213v1/x2.png)
*图2：对骨干模型冻结的最后一层隐藏状态进行线性探测。（左）沿 LDA 判别轴和一个正交方向的二维投影；（右）探测分数分布。两类样本的均值有明显差异，但中间波段存在重叠。*

为验证上述假设，作者从公开的 SWE-Bench 风格数据集中收集约 2,260 条多轮工具响应（约15.5万行），由 Claude Sonnet 4.6 标注每行的保留/剪枝标签。然后冻结 Qwen3-Coder-Next，对每行最后一层隐藏状态进行均值池化，拟合逻辑回归分类器。

结果表明：
- 两类样本在隐藏状态空间中有**明显不同的均值**（图2左：LDA 轴投影上分布偏移清晰）
- 在保留的测试轨迹上，探测器达到 **AUC 0.83、最优 F1 0.63**，显著超过多数类 F1 上界 0.46
- 这直接证明了"保留/剪枝信号已存在于骨干表示中"的假设

然而，线性探测无法解决中间波段的重叠区域，也无法利用工具输出的长度依赖结构，这两点共同motivate了 SWE-Pruner Pro 的非线性轻量头设计。

### SWE-Pruner Pro 架构

![方法总览](https://arxiv.org/html/2607.18213v1/x3.png)
*图3：SWE-Pruner Pro 总览。上方（智能体轨迹）：每轮骨干对 [history, c_t, r_t] 做 prefill，只有新工具响应 token 被前向传播，SWE-Pruner Pro 读取其最后一层隐藏状态。下方（SWE-Pruner Pro 头）：轻量头对每个隐藏状态打分，聚合为逐行保留/剪枝决策，剪枝后的响应替换下一轮的原始工具输出。*

**与现有方法的对比**：

![与SWE-Pruner对比](https://arxiv.org/html/2607.18213v1/x1.png)
*图1：（左）先前工作使用独立的 Pruner 模型，每轮需要智能体主动编写目标提示查询；（右）SWE-Pruner Pro 直接从智能体自身的内部表示中剪枝，无需外部评分模型。*

### 轻量剪枝头（Pruning Head）

![头架构](https://arxiv.org/html/2607.18213v1/x4.png)
*图4：头架构示意。骨干冻结的隐藏状态 h_i 加上以行数 N 为索引的长度感知嵌入，经过带 LayerNorm 和 Dropout 的两块前馈网络，输出逐 token 的保留分数，推理时在每行内部进行多数投票得到逐行决策。*

剪枝头包含两个关键设计：

**1. 长度感知嵌入（Length-Aware Embedding）**

$$\tilde{h}_i = h_i + \mathbf{e}(N)$$

其中 $\mathbf{e}(N)$ 是以工具输出行数 $N$ 为索引的可学习嵌入，广播加到每个隐藏状态上。零初始化确保训练初期退化为与长度无关的版本。

**设计动机**：误剪的代价高度依赖于 $N$——从5行输出中错误删除几行是灾难性的，而对300行输出做同样操作影响微乎其微。长度感知嵌入让头能吸收这种长度依赖关系。

**2. 逐token分类器 f_θ**

非线性结构：LayerNorm → 2层前馈（Linear-GELU-Dropout，隐藏维度与骨干一致）→ 单logit线性投影

$$z_i = f_\theta(\tilde{h}_i), \quad p_i = \sigma(z_i)$$

**逐行决策（行内多数投票）**：

$$\hat{y}_\ell = \mathbb{1}\left[\frac{1}{|\ell|}\sum_{i\in\ell}\mathbb{1}[p_i > \tau] > \frac{1}{2}\right]$$

### 训练策略

在 22,609 个来自真实多轮智能体轨迹的样本上训练剪枝头（每样本为一个 (history, tool_call, tool_response) 三元组），由 Claude Sonnet 4.6 提供逐行标注。

**核心损失函数：逐样本平衡焦点损失（Per-sample Balanced Focal Loss）**

关键洞察：keep/prune 的不平衡是**逐样本**的而非全局的。当一个样本中仅有3/100行被保留时，这3行携带了最强的"不可替换"信号；当90/100行被保留时，那10行携带了最强的"可安全删除"信号。标准交叉熵或批级焦点损失只看全局 keep 率（约30%），会被典型比例的样本主导，稀释极端比例样本中最有信息量的标签。

逐样本平衡焦点损失：分别对每个样本内部的 keep token 和 prune token 计算平均损失，再以等权组合：

$$\mathcal{L}_s = \frac{1}{2}\mathcal{L}_s^{\text{keep}} + \frac{1}{2}\mathcal{L}_s^{\text{prune}}$$

训练时骨干完全冻结，从缓存特征中训练头，无需对骨干进行任何微调或重训练。

### 服务器内集成（In-Server Integration）

SWE-Pruner Pro 在推理引擎内部运行：头直接在 prefill 时读取骨干已经计算的隐藏状态，无需额外的骨干前向传播，也避免了跨引擎边界传输隐藏状态。

## 总结

SWE-Pruner Pro 揭示了一个简洁而深刻的原理：编程智能体在被动读取工具输出时形成的内部表示，已经编码了先前方法需要花费额外模型调用才能恢复的相关性判断。这一洞察从根本上简化了上下文剪枝的实现路径——无需维护独立的评分模型，无需让智能体主动生成目标提示，只需在 prefill 过程中"顺路"从骨干表示中读取信号。

在工程实现上，SWE-Pruner Pro 将轻量头与骨干模型的推理引擎集成，避免了跨模型的隐藏状态传输开销，使得剪枝的额外延迟被控制在总生成时间的15%以内——而这15%的开销换来了后续轮次中高达39%的 token 节省，整体经济性显而易见。

从更广泛的意义看，本文的工作指向了一种新型的"内生式"智能体优化范式：不是在智能体之外搭建越来越复杂的辅助系统，而是充分挖掘智能体自身已经形成的内部知识。这一思路可以延伸到更多场景，如工具选择、推理方向评估、早停判断等，为构建更高效的下一代编程智能体提供了重要的方法论借鉴。
