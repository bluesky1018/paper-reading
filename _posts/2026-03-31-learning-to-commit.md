> 📄 **论文**：Learning to Commit: Generating Organic Pull Requests via Online Repository Memory
> 🔗 **arXiv**：[2603.26664](https://arxiv.org/abs/2603.26664)
> 🏢 **机构**：清华大学

## 一句话总结

通过让编码智能体在历史提交记录上持续学习、积累仓库专属技能记忆，使其生成的代码真正符合项目的架构惯例与风格规范，而不是语法正确但"格格不入"的外来代码。

---

## 背景与问题

### LLM 编码智能体的核心缺陷：缺乏"有机性"

当前基于大语言模型的编码智能体（如 SWE-agent、Devin 等）在各类基准上表现亮眼，但在真实生产仓库中却屡屡碰壁。论文将这一现象归结为缺乏 **有机性（Organicity）**，并将问题代码称为 **"外星代码"（alien code）**：

- **重复造轮子**：智能体不知道项目内部已有封装好的工具函数，直接重新实现
- **违背架构约束**：无视项目的模块化边界，随意跨层调用
- **风格格格不入**：命名规范、错误处理、测试组织方式均与项目惯例相悖

**根本原因**：智能体只能看到仓库的当前快照，看不到这个仓库*如何一步步演变*到当前状态——那些隐含在提交历史中的设计哲学、维护者偏好和编码规范，对它来说是完全不可见的。

### 现有评测框架的局限性

论文系统比较了现有框架（见下表），发现没有一个框架同时满足：按时间顺序评测、利用历史记忆、零数据泄露、使用 Oracle 监督、以及评估有机性。

| 框架 | 时序评测 | 历史记忆 | 零数据泄露 | Oracle监督 | 有机性评测 |
|------|---------|---------|-----------|-----------|-----------|
| SWE-bench | ✗ | ✗ | ✗ | ✗ | ✗ |

## 核心方法

### 问题形式化

将仓库的完整提交序列 $\mathcal{C} = (c_1, c_2, \ldots, c_T)$ 在时间点 $T^*$ 处切分：
- **历史前缀** $\mathcal{C}^-$：用于学习阶段，智能体从中积累技能
- **保留测试集** $\mathcal{C}^+$：用于评测阶段，时间上严格晚于学习数据

这种设计从结构上保证了**零数据泄露**，无需任何额外过滤。

每条提交包含三要素：仓库快照、Oracle diff（真实改动）、合成 Issue 描述（隐藏了实现细节的自然语言需求）。

### 框架总览

![框架总览](https://arxiv.org/html/2603.26664/x1.png)

*图1：Learning to Commit 框架示意——左侧为历史提交驱动的技能学习阶段，右侧为技能条件化的未来任务解决阶段，底部为多维度有机性评测。*

框架分为两个核心阶段：

---

### 第一阶段：通过对比反思完成仓库上手（Repository Onboarding）

对历史前缀中的每一条提交，执行三步循环：

**1. 盲尝试（Blind Attempt）**
智能体仅凭当前积累的技能，尝试解决该 Issue，生成候选 diff。

**2. Oracle 揭示（Oracle Revelation）**
向智能体展示真实的 Oracle diff，让其将自己的尝试与标准答案进行对比分析。

**3. 技能更新（Skill Update）**
智能体对技能文档 $\mathcal{M}$ 执行增删改操作：
- **新增**：记录之前未知的模式（如某个内部 API 的惯用法）
- **修订**：更新部分正确的条目
- **废弃**：删除被 Oracle 证明错误的条目

技能文档涵盖四类知识：
- 编码风格与命名惯例
- 内部 API 使用规范
- 架构约束
- 维护者偏好（错误处理方式、测试组织结构等）

---

### 第二阶段：技能条件化解决（Skill-Conditioned Resolution）

智能体在处理未见过的新任务时，将积累的技能文档 $\mathcal{M}$ 附加到上下文中，自主使用工具链解决问题。框架**不施加刚性检索管道**，而是让智能体自由决定如何利用技能知识。

---

### 数据集构建（五阶段流程）

1. **提交扫描与质量过滤**：从内部 RL 训练仓库扫描 2,738 条原始提交，筛选出 386 条高质量提交（适用率 77.2%）
2. **无监督类别聚类**：将提交聚为 7 类（架构、并发、测试等）
3. **LLM 类别标注**：对每条提交打上类别标签
4. **按类别分层采样与时序切分**：**24 条**用于学习，**7 条**用于测试
5. **合成 Issue 生成**：将 diff 转化为隐藏实现细节的自然语言 Issue 描述

---

### 评测指标设计

**确定性指标**：
| 指标 | 含义 |
|------|------|
| **File IoU** | 修改文件集合的 Jaccard 相似度，衡量定位精度 |
| **Trajectory Steps** | 总工具调用次数，衡量效率 |
| **Line Deviation Ratio** | 补丁大小相对 Oracle 的偏差，衡量代码膨胀程度 |

**LLM 评审（A/B 对比）**：
| 维度 | 评测内容 |
|------|---------|
| Q1: 范围对齐 | 修改范围与 Oracle 是否一致 |
| Q2: 逻辑相似度 | 实现逻辑是否与 Oracle 接近 |
| Q3: 冗余与幻觉 | 是否包含多余代码或虚构调用 |
| Q4: 代码风格 | 是否符合项目风格规范 |

## 实验结果

### 四种实验条件

| 条件 | 学习顺序 | 课程覆盖 |
|------|---------|---------|
| seq-all | 顺序 | 全量语料 |
| seq-bycat | 顺序 | 按类别 |
| par-all | 并行 | 全量语料 |
| par-bycat | 并行 | 按类别 |

基线：不附加技能文档的 Claude Opus 4.6；技能智能体：附加积累记忆 $\mathcal{M}$ 的相同模型。

---

### 确定性指标结果

| 设置 | File IoU（技能/基线） | Steps（技能/基线） | Line Dev.（技能/基线） |
|------|---------------------|-----------------|---------------------|
| seq-all | **80% / 61%** | **56.8 / 71.9** | **0.69 / 1.59** |
| par-bycat | **80% / 68%** | 62.7 / 62.7 | **0.62 / 0.88** |
| par-all | **81% / 72%** | **67.7 / 68.3** | **0.80 / 1.06** |
| seq-bycat | 71% / 71% | **75.0 / 76.4** | 1.22 / **1.13** |

**关键发现**：
- File IoU 最多提升 **+19%**（seq-all 设置），说明技能记忆显著提升了文件定位精度
- Line Deviation Ratio 在多数设置下大幅降低，说明技能智能体生成的补丁更精简，减少了代码膨胀

---

### LLM 评审胜率

| 设置 | Claude 评审（技能胜率） | Gemini 评审（技能胜率） |
|------|----------------------|----------------------|
| par-bycat | **54%** | **57%** |
| seq-all | **55%** | **58%** |
| par-all | 46% | **54%** |
| seq-bycat | 26% | 46% |

---

### 各维度细化结果（par-bycat 设置）

| 维度 | 技能胜 | 基线胜 | 平局 |
|------|--------|--------|------|
| Q1: 范围对齐 | 25% | 41% | 34% |
| Q2: 逻辑相似度 | **50%** | 25% | 25% |
| Q3: 冗余与幻觉 | **54%** | 41% | 5% |
| Q4: 代码风格 | 27% | 38% | 36% |

**结论**：技能记忆的最大价值在于**减少冗余与幻觉**（Q3）和**提升逻辑相似度**（Q2），而对表面代码风格的影响有限。Q3 是跨评审模型一致性最高的维度。

---

### 典型案例分析

**最佳案例：共享 RNG 并发 Bug 修复**
- 技能智能体正确定位到 judge client 模块，实现 100% File IoU
- 基线模型错误地修改了无关的 API 模块，File IoU 为 0%
- 体现了技能记忆在代码定位上的决定性优势

**最差案例：训练步骤守卫逻辑**
- 技能智能体保留了一个冗余的防御性守卫，代码略比基线冗长
- 体现了技能记忆并非万能，在精细粒度的逻辑判断上仍有改进空间

## 总结

### 核心贡献

1. **提出"有机性"概念**：明确定义了编码智能体在真实仓库中缺失的关键能力，填补了现有评测框架的重要空白。

2. **在线仓库记忆机制**：通过对比反思循环，让智能体在历史提交上持续学习并积累结构化技能文档，无需任何模型微调。

3. **严格的零泄露评测设计**：时序切分从构造上保证评测公平性，且覆盖了确定性指标与 LLM 评审的多维度评测体系。

4. **不对称增益发现**：技能记忆对"改哪里"（文件定位）和"用什么"（避免冗余）帮助最大，对表面代码风格影响有限，揭示了未来提升方向。

### 局限性与未来工作

- 当前实验仅在单一内部仓库上验证，需扩展至多样化的公开 GitHub 仓库
- 有机性评测仍依赖 LLM 评审，需开发更鲁棒的非 LLM 指标
- 技能迁移能力（能否跨仓库复用技能）尚未探索
