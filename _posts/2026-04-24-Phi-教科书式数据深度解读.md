## 基本信息

- **作者**: Suriya Gunasekar, Yi Zhang 等(Microsoft Research)
- **机构**: Microsoft Research
- **发表**: arXiv 2023-06
- **arXiv**: [2306.11644](https://arxiv.org/abs/2306.11644)
- **全名**: *Textbooks Are All You Need*

## 一句话总结

Microsoft 的 **Phi** 系列开山之作——**用"教科书级"合成数据训练 1.3B 模型,代码能力超过 16B 和 70B 的开源模型**。核心观点:**模型质量的瓶颈不是参数量,而是数据质量**。具体做法:用 GPT-3.5 生成"教科书风格"的 Python 编程教材(10B tokens),再配上合成练习题(1B tokens),总 6B tokens 训练 Phi-1 (1.3B 参数),HumanEval 从 baseline 的 ~0% 跳到 **50.6%**——打过 LLaMA 16B (18%)、Falcon 40B (28%)、LLaMA 2 70B (29%)。Phi 证明了 **"data quality is all you need"** 思想的极致——开启 Phi-1.5 / Phi-2 / Phi-3 / Phi-4 系列,成为"小模型打大模型"的代表作,也是合成数据训练路线的里程碑。

## 背景:大力出奇迹 vs 数据质量

### "大"的代价

2023 年大模型训练:

- LLaMA 65B:1.4T tokens,1000 GPUs × 21 天
- MPT 30B / Falcon 40B 类似
- 数百万美元/次

**大 = 贵**。如果能用小模型做同样的事,经济意义巨大。

### 质量 vs 规模的 trade-off

Phi 团队的观察:

- 大模型训练用的是 **Common Crawl 这样的"互联网常见内容"**
- 这些内容**平均质量**很一般——大量重复、噪声、低价值
- 如果能用**高质量、教科书级别**的内容,也许小模型就够

**关键 bet**:data quality 的价值可能大于 data quantity。

---

## 核心机制:用 GPT 生成"教科书"

### Phi-1 的训练数据(总 6B tokens)

**1. The Stack / filtered**(~3B tokens)
- 从 The Stack 数据集筛选 "educational" 代码(用 GPT-4 classifier 打分)
- 只保留高质量部分

**2. Synthetic Textbooks**(~1B tokens)
- 用 **GPT-3.5** 生成 Python 编程教科书
- Prompt:"写一段关于排序算法的教科书内容,包含解释和代码示例"
- 多样化 topic 覆盖

**3. Synthetic Exercises**(~180M tokens)
- 用 **GPT-3.5** 生成 Python 练习题 + 解答
- Docstring + 测试 + 解题代码

![Phi-1 的数据示例:合成的"教科书段落"包括概念解释、代码示例、应用场景。这种 "denser" 的内容比原始 GitHub 代码信息密度高得多。](/assets/img/phi/x2.png)
_Figure 2:合成教科书样本_

### 为什么"合成教科书"有效

1. **信息密度高**:真实代码有很多重复、boilerplate——教科书每句都承载知识
2. **覆盖均衡**:人造内容可以覆盖 rare 概念,真实数据里冷门概念太少
3. **风格一致**:统一的"解释 + 例子"格式让模型学得快
4. **无污染**:合成数据没有 license 问题、没有 benchmark 泄漏

---

## 训练配方

- **Model**:1.3B 参数 Transformer(类似 LLaMA 架构)
- **Data**:6B tokens(远小于 LLaMA 的 1.4T)
- **Epochs**:几个 epoch 多次看数据
- **Compute**:**单台 A100 机器 4 天**——比 LLaMA 训练便宜 100+×

## 实验结果

### HumanEval

| 模型 | 参数 | HumanEval |
|------|------|-----------|
| GPT-3.5 | ? | 47.0 |
| LLaMA 7B | 7B | 14.0 |
| LLaMA 13B | 13B | 15.6 |
| LLaMA 65B | 65B | 23.7 |
| LLaMA 2 70B | 70B | 29.9 |
| Falcon 40B | 40B | 22.6 |
| **Phi-1** | **1.3B** | **50.6** |

**1.3B 的 Phi-1 超过 70B 的 LLaMA 2**——这个对比极具震撼。

### MBPP

- Phi-1:55.5%
- LLaMA 2 70B:56.4%

几乎持平——50× 小的模型在编程 benchmark 上持平大模型。

## 后续工作:Phi 系列

Phi-1 之后,Microsoft 继续沿这条路:

### Phi-1.5(2023-09)
- 从 code-only 扩展到 general reasoning
- 仍然 1.3B 参数
- 加入合成的常识、推理数据

### Phi-2(2023-12)
- 2.7B 参数
- 更广泛合成数据
- 通用能力匹敌 7-13B 模型

### Phi-3(2024-04)
- 3.8B 参数
- MMLU 69%,对标 8B 开源模型

### Phi-4(2024-12)
- 14B 参数
- MATH 级别推理
- 9.8T tokens 训练,**80% 合成数据**

## 工程影响

### 1. 证明 "data > scale"

Phi 之前,业界默认"越大越好"。Phi 证明**小模型 + 好数据 > 大模型 + 烂数据**——这个观察直接改变了预训练策略。

### 2. 合成数据成为主流

Phi 之后,几乎所有大模型公司都开始:

- 用 GPT-4 / Claude 等强模型**生成**合成数据
- 用 classifier **筛选**高质量网页数据
- **Phi-4** 更激进——80% 数据是合成的

合成数据从"辅助"变成"主力"。

### 3. 小模型研究复兴

Phi 让"小模型(< 5B)也能很强"成为可能。这催生:

- **Gemma 2B / 7B**(Google)
- **Qwen 1.5B / 4B**(Alibaba)
- **Mistral 7B**(更好数据)
- **SmolLM**(HuggingFace)

一整条"小而精"的开源模型赛道。

### 4. 对"数据墙"的一种回应

2023-2024 年业界担忧 "高质量互联网文本要枯竭"(Villalobos 2022 预测)。Phi 的合成数据路线给出一条路:**如果真实数据不够,就造**。

### 5. 推动质量评估工具

Phi 团队用 GPT-4 做数据 classifier —— 这启发了后续一系列 "LM as judge" 工作,用于 data filtering、post-training 等。

---

## 局限

### 1. Benchmark "污染" 争议

Phi 的 HumanEval 成绩引发争议——**合成数据可能包含与 HumanEval 题目高度相似的内容**,导致 benchmark 失真。后续 live benchmark(LiveCodeBench)显示 Phi 性能没这么惊艳。

### 2. 窄域能力

Phi-1 只强在 Python coding。通用能力(闲聊、推理)远不如同 size 模型。Phi-1.5+ 扩展了通用性,但仍有窄域痕迹。

### 3. 合成数据的 "知识天花板"

合成数据来自 GPT-4/Claude——**上限就是这些模型的知识**。无法超越 teacher 模型。

### 4. 多样性不足

合成数据的**风格可能过于统一**(GPT-4 的偏好),导致模型在 out-of-distribution 数据上表现差。

---

## 读完这篇你真正该带走的 4 件事

<callout emoji="white_check_mark" background-color="light-green" border-color="green">
1. **数据质量是 LLM 的最大变量**:1.3B 模型 + 6B 高质量 tokens 打过 70B 模型 + 1.4T 中等质量 tokens——数据质量的影响是数量级的
2. **"教科书级"合成数据是有效的数据源**:用强模型生成的高信息密度内容,填补互联网数据的质量漏洞。这个思想在 Phi-4 推到 80% 合成数据的极致
3. **小模型的价值被重新发现**:Phi 让业界重新认识到"小而精"模型的巨大经济和部署价值。这催生了 SLM(Small Language Model)赛道
4. **Benchmark 污染是合成数据时代的新挑战**:Phi 的争议提醒我们——**要用 fresh、live benchmark 而非静态 benchmark 评估模型**。LiveCodeBench 等工作就是对这个问题的回应
</callout>
