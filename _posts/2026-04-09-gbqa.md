> 📄 **论文**：GBQA: A Game Benchmark for Evaluating LLMs as Quality Assurance Engineers
> 🔗 **arXiv**：[2604.02648](https://arxiv.org/abs/2604.02648)
> 🏢 **机构**：香港大学 & Datawhale Org、独立研究者、西湖大学

## 一句话总结

GBQA 是首个以互动游戏环境为测试床、系统评估 LLM 自主发现软件 Bug 能力的基准，包含 30 款游戏和 124 个经人工验证的 Bug，当前最优模型（Claude-4.6-Opus 思维模式）的 Recall 仅为 48.39%，表明 Bug 发现仍是 LLM 面临的重大挑战。

## 背景与问题

现代软件开发正在经历深刻变革。以"vibe coding"为代表的人机协作编程模式已显著提升了代码生成效率，大量研究（如 SWE-bench）也证明 LLM 在 Bug 修复方面具有相当潜力。然而，软件开发流程中同样关键的另一环——Bug **发现**（Quality Assurance，QA）——却远未得到充分探索。

与 Bug 修复不同，Bug 发现是一个目标不清晰的开放式任务：工程师需要主动与软件交互，观察异常行为，并区分"设计如此"与"程序缺陷"。这要求模型具备深度的状态追踪、长时域推理和异常感知能力，而非仅根据预定义的问题描述输出修复方案。

游戏软件天然成为这一任务的理想测试床：游戏拥有明确的状态空间（State）、动作空间（Action）和转换规则（Transition），状态具有持久性，且行为规格（即游戏设计文档）可作为基准真相（ground truth）。本文提出的 GBQA 基准正是利用这一特性，系统评估 LLM 在真实交互环境中自主发现软件缺陷的能力。

## 核心方法

### 3.1 任务定义

GBQA 将游戏形式化为四元组 $(S, A, T, s_0)$，其中 $S$ 为状态空间，$A$ 为动作空间，$T: S \times A \to S$ 为转换函数，$s_0$ 为初始状态。智能体通过探索生成 Bug 报告集合 $R$，评估指标为与真实 Bug 集合 $B$ 的 Recall：

$$\text{Recall} = \frac{|B^+|}{|B|}$$

其中 $B^+$ 为正确识别的 Bug 子集。之所以优先考虑 Recall 而非 Precision，是因为"漏报缺陷的代价远高于误报"——这与真实工程场景高度一致。

评估支持两种模式：
- **Player Exploring Mode（玩家探索模式）**：不提供任何文档，智能体仅凭交互体验发现异常
- **Quality Assurance Mode（质量保证模式）**：提供设计规格说明书和源代码，智能体以专业 QA 工程师身份工作

### 3.2 游戏环境构建系统

为可扩展地构建高质量游戏环境，论文设计了层级多智能体系统（Hierarchical Multi-Agent System），由以下角色组成：

- **Producer Agent（制作人智能体）**：统筹整体设计，分配任务
- **Design Team**：负责游戏机制设计与文档编写
- **Programming Team**：负责前后端代码实现，严格采用前后端分离架构，Backend Endpoint 作为智能体的动作工具
- **Art Team**：负责界面与视觉资产

所有游戏均部署为 Web 应用，涵盖 6 大类型：动作（Action）、冒险（Adventure）、角色扮演（RPG）、策略（Strategy）、模拟（Simulation）和益智（Puzzle）。

*图2：软件开发范式演进——(a) 传统人工驱动模式，(b) 人机协作模式，(c) 全自动 LLM 驱动模式。GBQA 重点评估阶段 (c) 中的 Bug 发现能力*

### 3.3 基准数据统计

| 维度 | 数量 |
|------|------|
| 游戏总数 | 30 |
| Bug 总数 | 124 |
| 游戏类型 | 6 |
| 难度等级 | 3（Easy / Medium / Hard）|

**难度分类体系：**

| 难度 | 描述 |
|------|------|
| Easy（简单）| 单次观测即可发现的表面不一致，如 UI 显示错误 |
| Medium（中等）| 需要短时域推理的游戏逻辑违规，需执行特定操作序列 |
| Hard（困难）| 需要跨扩展轨迹进行长时域一致性追踪 |

### 3.4 真实标注与质量保证

三位专业 QA 工程师独立验证每个 Bug 候选，分歧通过多数投票解决。最终标注一致性 Krippendorff's α = 0.901，达到高度一致水平。

### 3.5 Baseline 智能体设计

论文为 GBQA 设计了专用基线智能体，核心包含两大组件：

**ReAct 循环与反思机制：**

每次状态转换后，智能体执行以下流程：
1. 判断实际结果是否符合预期
2. 若发现异常，形成 Bug 假设（包含：触发动作、观察行为、预期行为、违规类型）
3. 本地验证假设
4. 提交 Bug 报告

**层级记忆系统（Hierarchical Memory）：**

| 记忆类型 | 描述 |
|----------|------|
| In-Session Memory（会话内记忆）| 滑动窗口 + 旧步骤摘要；保留因果链（如道具→事件链） |
| Cross-Session Memory（跨会话记忆）| 持久化存储，记录已探索区域、已确认 Bug 和未探索分支；注入后续会话 |

![Bug 发现率与步骤预算关系](https://arxiv.org/html/2604.02648/x3.png)
*图3：不同难度级别的 Bug 发现率随步骤预算变化曲线——Easy 类 Bug 在约 300 步内趋于饱和，Hard 类 Bug 在 500 步时仍未出现收敛迹象*

## 实验结果

### 5.1 主要结果

以下为各模型在最优步骤预算下的 Recall 表现：

| 模型 | 最优 Recall (%) |
|------|-----------------|
| Claude-4.6-Opus-Thinking | **48.39** |
| Qwen3.5-397B-A17B-Thinking | 41.13 |
| DeepSeek-R1 | 37.90 |
| Claude-4.5-Sonnet-Thinking | 37.10 |
| GPT-5.2 | 22.58 |
| Llama-3.1-70B | 14.52 |
| Qwen3-32B-Thinking | 13.87 |
| Llama-3.1-8B | 8.87 |

**关键发现：**

1. **所有模型均低于 50% Recall**，表明自主 Bug 发现显著难于 Bug 修复（前沿模型在 SWE-Bench Verified 上已超过 70%）
2. **Thinking/推理模式全面优于 Instruct 模式**，验证了思维链在复杂探索任务中的价值
3. **QA Mode 优于 Player Exploring Mode**，提供文档和源代码使智能体能更有针对性地测试
4. **推理时缩放（inference-time scaling）比参数缩放更高效**：Qwen3-32B-Thinking（33.87%）优于 Llama-3.1-70B（14.52%），以更少参数取得更高性能

### 5.2 两种评估模式对比

| 模型 | Player Exploring Mode (%) | QA Mode (%) |
|------|--------------------------|-------------|
| Claude-4.6-Opus-Thinking | ~38 | **48.39** |
| DeepSeek-R1 | ~28 | **37.90** |
| GPT-5.2 | ~15 | **22.58** |

### 5.3 Critic 智能体可靠性

为实现可扩展的自动化评估，论文训练/评估了多个模型作为 Critic 智能体（自动打分器），与人工评分的 Pearson 相关系数如下：

| Critic 模型 | Pearson ρ |
|-------------|-----------|
| GPT-5.2 | **0.903** |
| Claude-4.5-Sonnet | 0.876 |
| Qwen3.5-72B | 0.851 |

GPT-5.2 作为 Critic 与人工评分高度一致（ρ = 0.903），被采用为默认评估器。

### 5.4 记忆消融实验

![记忆消融实验](https://arxiv.org/html/2604.02648/x4.png)
*图4：四种记忆配置（无记忆、仅 In-Session、仅 Cross-Session、完整记忆 IS+CS）的 Bug 发现趋势——完整记忆配置在所有会话中始终保持最高发现率*

| 记忆配置 | 相对 Recall |
|----------|------------|
| 无记忆 | 最低 |
| 仅 In-Session (IS) | 中等 |
| 仅 Cross-Session (CS) | 中等偏高 |
| IS + CS（完整）| **最高** |

结论：两种记忆机制存在互补性，完整记忆系统显著优于任何单一组件。

### 5.5 步骤预算分析

- **Easy Bug**：约 300 步后发现率趋于饱和，继续增加步骤预算收益递减
- **Hard Bug**：即使在 500 步时仍未出现收敛，说明长时域 Bug 需要更高效的探索策略

## 总结

GBQA 填补了 LLM 评估领域在主动式 Bug 发现任务上的空白。通过以游戏为测试床，结合严格的人工验证标注体系和精心设计的多难度分类，该基准为衡量 LLM 作为 QA 工程师的实用潜力提供了可靠工具。最优模型 Claude-4.6-Opus（思维模式）仅达到 48.39% Recall，清晰揭示了当前 LLM 在主动式软件测试方面的重大能力缺口。

该研究的主要贡献在于：(1) 提出了首个面向 Bug 发现的互动游戏基准；(2) 设计了可扩展的多智能体游戏构建与 Bug 注入流水线；(3) 提出了层级记忆基线智能体；(4) 揭示了推理时缩放在复杂探索任务中优于单纯参数缩放的规律。

局限性方面，当前基准仅包含 30 款游戏（124 个 Bug），规模相对有限；游戏均为 Web 应用形式，可能无法完全覆盖真实工业软件的复杂性；此外，硬难度 Bug 在 500 步内未见收敛，暗示当前基线智能体的探索策略仍有较大改进空间。未来工作可以考虑扩展游戏类型与 Bug 数量、引入更高效的探索算法，以及探索将代码静态分析与动态交互探索相结合的混合策略。
