## 一句话总结

Foundation Protocol（FP）提出了一个以图优先的协调层，通过 7 个核心语义对象和 4 平面架构统一管理智能体社会中的身份、交互、经济和监管需求，在不替换 MCP、A2A 等现有协议的前提下通过包裹和桥接实现渐进式采用，核心目标是让"自主智能体可组合，同时让问责制不可妥协"。

## 背景与问题

当今 AI 智能体已不仅仅是问答系统，它们浏览网页、购买商品、部署软件、管理基础设施，并将子任务委托给其他智能体。一个单一的智能体工作流可能需要工具调用、智能体间委托、UI 控制、身份验证、支付授权和策略执行——所有这些都在一条动作链中发生。然而，管理这些交互的统一协调基础设施至今仍不存在，这已成为核心瓶颈：模型能力快速进步，但确保智能体安全、可组合和可问责的协议层远未跟上。

论文将这一挑战置于宏观历史背景下：每一次工业革命都引入了新的生产能力，最终需要新的协调基础设施。蒸汽时代需要标准化铁路轨距，电气时代需要正式技术标准，计算时代需要网络协议。今天的"第五次工业革命"——智能体作为经济和社会行为者的崛起——同样需要专门的协调层。

从 Web 演进的教训同样值得借鉴：能力总是先于治理基础设施到来，产生危险的空白期。Web 2.0 将读者变为参与者但将权力集中到监控驱动的平台；Web 3.0 追求去中心化但陷于碎片化；正在出现的 Web 4.0"代理式网络"让系统能够"代表我们行动、决策、调解关系"。关键教训是：一旦自主权分散到众多自主行为者中，身份、策略和溯源必须成为通信基础设施本身的组成部分，而不能事后再添加。

## 核心方法

### 7 个核心语义对象

| 对象 | 作用 |
|------|------|
| **Entity（实体）** | 具有身份、能力元数据和隐私控制的可寻址参与者 |
| **Session（会话）** | 绑定参与者、角色、策略引用和预算的多方作用域上下文 |
| **Activity（活动）** | 具有显式状态转换和类型化 I/O 的工作单元 |
| **Envelope（信封）** | 承载意图、路由/关联 ID 和策略引用的签名包装器 |
| **Event（事件）** | 支持流式传输、重放和背压的只追加观测记录 |
| **Receipt/Settlement（收据/结算）** | 可验证的计量使用和价值交换记录 |
| **Provenance（溯源）** | 决策、审批和撤销的结构化审计记录 |

### 四平面架构

![FP四平面架构](https://arxiv.org/html/2605.23218/x2.png)
*图：Foundation Protocol 四平面架构示意图*

**实体与信任平面**：每个参与者——智能体、人类、工具或组织——都用统一可寻址的 Entity 表示，具有加密身份（Ed25519 密钥）、版本化能力声明、信任信号和隐私控制。渐进式披露允许先提供轻量级能力摘要，授权后才获取完整模式。

**传输与路由平面**：传输无关设计，具体绑定由配置文件提供。支持在单个群组会话中混合传输（本地 IPC、HTTP、WebSocket、SSE），同时保持顺序性、背压和终止语义。

**交互与组织平面**：会话是显式的多方容器，具有角色、策略引用和预算限制。经济原语——计量、收据、结算引用、争议信号——是一等公民，账本无关。

**监管与监督平面**：策略评估发生在协议边界处，在调用或结算前执行。溯源记录可引用、可哈希、可独立验证。争议、撤销和安全报告是一等事件，同一审计轨迹在不同策略下可检查。

### AI 软件公司场景演示

![FP应用场景](https://arxiv.org/html/2605.23218/x3.png)
*图：AI 软件公司场景生命周期（建立→发现→协作→执行→结算→审计）*

论文通过一个五阶段的 AI 软件公司场景展示 FP：
1. **建立**：人类创始人注册为 Entity，创建带治理策略的组织实体，注册三个内部智能体（规划者、开发者、审查者）
2. **发现与招募**：规划者查询 GPU 供应商和 MCP 兼容代码搜索工具，接收轻量级元数据
3. **协作**：任务分配，开发者通过 MCP 桥接调用外部工具，部署前需人类审批
4. **经济活动**：GPU 供应商报告计量使用（计算小时数、Token 消耗），预算上限通过支付检查点强制执行
5. **审计**：所有策略决策、审批、授权和拒绝均作为带溯源的事件记录，创始人可查询任意实体在何策略下产生何种经济结果

## 实验结果

本文为协议设计与立场论文，不报告传统 ML 数值评测结果。主要量化特征：

- 29 位作者，来自 10+ 机构
- 7 个核心语义对象
- 5 个声誉维度（均从合同事实派生）
- 3 个安全层级（信封级签名+加密、合同审计轨迹、检查点级可追溯性）
- 合同状态机：6 个状态（DRAFT→PENDING→ACTIVE→COMPLETING→SETTLING→SETTLED），2 个终态故障分支

## 总结

Foundation Protocol 提出了面向智能体社会的紧凑协议核心，涵盖五大支柱：统一实体模型、原生组织原语、事件驱动交互、账本无关的经济证明以及协议级监督与审计。与其建立替换现有协议的庞大单体，FP 作为协调层包裹和桥接 MCP、A2A、DIDComm、ANP 等，实现渐进采用，同时将身份、策略、溯源和经济原语纳入共享基础设施。

核心设计哲学是："在不让问责制成为可选项的前提下，使自主智能体可组合。"作者认为这不仅是工程上的便利，更是安全边界——因为在智能体系统中，一条消息可能触发代码执行、资源消耗、支付、委托或策略变更。下一步计划包括开发精确规范和参考绑定，供生态系统评估和社区实现。
